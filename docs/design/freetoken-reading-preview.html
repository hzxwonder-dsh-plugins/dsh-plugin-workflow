快速阅读

  • 问题： MoE 每次只计算少数专家，但整套专家权重仍远超显存。长输入近乎遍历整个专家池；逐词生成又会遇到缓存未命中。
  • 核心办法： 预填阶段让整层搬运与计算重叠，并复用代理会话中仍然有效的状态；生成阶段用共享缓存和机器实测带宽决定未命中专家由 GPU 还是 CPU 处理。
  • 最强证据： 论文在 RTX 5090 上报告 Qwen3.6-35B-A3B 的生成速度为 77–83 token/s、DeepSeek-V4-Flash 为 22–25 token/s；双缓冲消融、同路由轨迹缓存对照和跨硬件实验分别检验主要设计。
  • 边界： 这些结果属于指定模型、精度、六台机器和四类负载。能否在别的机器重现，需要看显存、主机带宽、PCIe、权重格式和实际请求形态。

从开放权重到可用服务，中间缺什么？

一个人可以下载开源模型，并不等于他的电脑能持续、流畅地运行它。写代码的代理会反复读取仓库、调用工具、删改历史上下文；每次等待首个输出都可能让交互停顿。FreeToken 的研究问题是：怎样把个人电脑的 GPU、CPU、主机内存和 PCIe 当成一套系统，而不只是把数据中心程序塞进较小的显卡？（原论文 §1）

混合专家模型（MoE）提供了机会。一个 MoE 层拥有许多“专家”，路由器对每个 token 只选择少数专家计算。论文举例：DeepSeek-V4-Flash 有 284B 总参数，每个 token 只激活约 13B；43 个 MoE 层中，每层从 256 个路由专家里选择 6 个。少算不等于少存：完整权重仍要放在主机内存或存储设备中，显存只容得下其中一部分（§1）。

原论文 Figure 1 展示研究定位。左侧把模型能力和 API 使用价格放在一起，右侧按硬件层级比较代理负载上的生成速度；读图时不要把不同任务、不同模型的点当作同一实验。它说明论文想推动的是“能够服务哪些模型”和“能否交互地服务”两个边界，并不能单凭这张图推断总拥有成本。

三个真正让本地 MoE 变慢的环节

第一，长输入让“稀疏”在权重访问上变得近乎稠密。 单个 token 只访问少数专家，但几千个 token 的路由并起来可能覆盖每层大部分专家。预填（prefill）是模型处理整段输入、产出第一个 token 前的阶段；完整专家池大于显存时，几乎所有专家权重都要跨 PCIe 搬一次。论文估计某个 FP4 的 DeepSeek-V4-Flash 部署需搬约 140 GB，在 RTX 5090 级连接上约两秒，在较窄链路上更久（§2.1）。

第二，逐词生成时路由重新变稀疏，但未命中仍昂贵。 解码（decode）每次只生成一个 token，所需专家不在显存时，要么沿 PCIe 搬到 GPU，要么让 CPU 从主机内存直接计算。已有静态放置方法可能跟不上实时路由；只靠 CPU 则受普通电脑少数内存通道限制。论文指出，预测下一次访问可以减少未命中，却不能回答剩余未命中该怎样执行（§2.2、§6）。

第三，个人电脑的资源不断变化。 浏览器和桌面应用会抢显存；会话越长，保存上下文的 KV 缓存越大，留给专家缓存的空间越少。重新启动又要从磁盘读入整个专家池。一个启动时固定好的显存划分，无法一直适配这种变化（§2.3）。

论文的洞察与贡献分别是什么？

这篇论文不是把一种缓存算法用于所有阶段。作者观察到：预填与解码访问权重的方式相反；代理在工具调用边界编辑上下文；相邻解码 token 的专家路由存在短期局部性；主机内存带宽与 PCIe 带宽之差可供 CPU 处理一部分未命中。它们是设计依据，不应直接当成性能结果（§2–3）。

论文的贡献是上述机制的系统组合以及可随目标机器变化的分工策略。例如 LRU、前缀树和 CPU 专家计算本身都有先例；新意在于它们如何适配代理负载、两个推理阶段与异构带宽（§3、§6）。

先看全景：权重、缓存和状态各放在哪里

主机内存保存完整专家池，是权重的“源头”；非专家权重长期留在 GPU。余下显存构成一个跨所有 MoE 层共享的专家缓存，缓存槽以“层号＋专家号”识别，而不是把一个专家的张量拆成互不相关的碎片。输入阶段从同一槽池临时借出两层缓冲；生成阶段槽池恢复为按最近使用更新的缓存（§3）。

一个贯穿例子：一次代理工具调用之后

设想一个编码代理读入较长的仓库上下文，随后调用工具，再把较早的一段工具输出替换成摘要。以下顺序是便于理解的教学示意，具体数字另以论文图表为准。

  1. 新请求先查找仍然相同的前缀。完整注意力层可复用此前保存的 KV；循环层从改动之前最近且仍有效的语义检查点恢复状态。改动后的文本重新预填。
  2. 预填层 正在 GPU 上运行时，下一层 的专家权重在另一块缓冲中通过 PCIe 搬运；层切换时交换缓冲。
  3. 开始逐词生成后，路由器选出当次专家。显存里已有的专家直接在 GPU 上执行；其余构成未命中集合。
  4. 系统根据机器实测带宽，为一部分未命中专家分配缓存槽并搬到 GPU；剩余的在 CPU 上就地计算。两侧部分输出按原路由权重合并。
  5. 新填充的专家留在共享缓存中。后续 token 再次路由到它时便可命中；若显存被别的应用占用，缓存可在调度安全点按新预算重建。

这个例子串起论文的三条线：避免重复算已有上下文、隐藏不可避免的权重搬运、并发利用仍可用的主机带宽。接下来分别看每条线的实现与适用条件。

长输入阶段：为什么整层加载反而合理？

逐 token 看，MoE 路由很稀疏；整段长输入看，许多 token 的专家需求求并集后接近整层专家池。所以在预填阶段逐个按需拉专家，可能产生大量小搬运和等待。FreeToken 为当前层与下一层各留一个整层缓冲，专门的传输流一边搬下一层，一边让 GPU 计算当前层。这里利用的是不同层之间的时间重叠，不是减少必须读取的专家总量（§3.1）。

下一层的路由尚未完成时，整层搬运仍然能先开始，这避免了“先等路由，再决定搬哪个专家”的串行链。两块缓冲从全局槽池借用，预填结束后存活的条目还能成为解码缓存的初始内容。所需前提是显存能同时容纳两层；预算不足时退回按需加载（§3.1）。

为什么代理编辑历史时还要保存循环状态？

传统全注意力层可以把前缀的 KV 项按位置缓存，但一些混合架构含循环层：它把此前信息压缩成随 token 演进的状态。历史中间某处被改写后，改写点之后的状态失效。若检查点太稀，系统就得从更早处重新计算大量 token（§2.1）。

FreeToken 将少量完整循环状态检查点附着到前缀树的语义边界：思考段、工具调用、工具结果和会话轮次。代理常在这些边界替换整个区块，因而改动点之前的检查点更可能仍然有效。新请求选择最深的有效检查点，循环层从此恢复，全注意力层复用相应 KV，之后只重算新的后缀；检查点槽位独立地按 LRU 回收（§3.1）。

Q：缓存过的前缀是不是编辑之后都能复用？

A：只能复用改动点以前仍完全相同的部分。完整注意力与循环层需要各自有效的缓存或检查点；位置越早、检查点越稀，重算后缀越长。

逐词生成阶段：先命中，再分工

解码时，GPU 上的路由和查表找出当前层实际需要的专家。已在缓存中的集合先执行；未命中专家才需要调度。FreeToken 用跨层共享的 LRU 空间跟踪最近使用的“层＋专家”对：命中刷新最近使用顺序，搬入占用槽位，空间不足时淘汰最久未用者。短期重复的路由有机会直接命中，而非每次从主机搬运（§3.2）。

LRU 也不是万能的。冷启动、工作集突变或显存容量很小时仍会未命中；缓存命中率只能解释“要处理多少未命中”，不能解释“怎样最快处理这些未命中”。因此论文把缓存策略和执行分工分成两层问题。

Q：为什么不把所有未命中都搬到 GPU，让下一轮更容易命中？

A：那会把当前 token 的等待集中到 PCIe 上。论文利用传输之后剩余的主机带宽并行完成部分专家计算，同时保留至少一次填充来积累未来命中。

实现细节：动态路由如何留在 CUDA Graph 里？

上面的分工每个 token、每个 MoE 层都可能不同。如果每次都把未命中列表送回 Python 决策，就会出现大量设备同步和主机调度开销，足以吃掉理论带宽收益。FreeToken 把路由相关控制表示为固定形状工作区中的数据和设备侧有效数量，使变化的任务能在静态捕获的 CUDA Graph 中重放（§4.1）。

一个 GPU kernel 去重当前路由，查缓存、计算 、选淘汰槽位，并把逻辑专家号改写为物理槽位或 CPU 标记。为避免每淘汰一个槽位都扫描整个缓存，它一次找出需要的最久未用候选，再取前 个；复制任务合并成一次传输，未用的固定形状位置由有效数量屏蔽。CPU 分支也在图里：固定的 I/O 缓冲、任务描述符、提交节点和结果回传，与 GPU 分支同步合并。CPU 工作者是长期运行的 C++ 线程池（§4.1）。

权重存储也参与了这条路径。FTW 格式预先把不同模型检查点整理成以“层＋专家”为首维的专家 bank，启动时直接读到最终主机布局，填满之后再固定内存；这样减少重新排布和给空缓冲预先分配页面的成本。若操作系统或驱动不能为完整专家池建立快速 DMA 路径，论文描述的后备模式让专家全部在 CPU 执行；因此硬件规格表上的 PCIe 数字并不自动保证快速路径可用（§4.2）。

显存预算变化时发生什么？

非专家权重和运行时状态占用显存之后，剩余预算要在 KV 页面与完整专家槽位之间分配。FreeToken 可在调度安全点按照新的可用显存重建专家缓存和捕获的执行路径，主机专家池不必重载。正确性依赖主机权重始终存在，GPU 缓存大小主要影响速度。冷缓存也能由普通未命中路径服务，随后逐渐升温（§3.3）。

这些设计回答“个人电脑上能不能持续运行”的工程问题。不过本文后面的 Figure 3–5 主要测试端到端速度、预填流水线、专家局部性与跨硬件表现；不能把这些综合图直接解释为 FTW 或动态重建各自带来了多少秒收益。

实验先看条件：比较的是哪些运行？

论文的主要端到端比较放在 RTX 5090 上，跨硬件实验共覆盖六台离散 GPU 机器：3090、4090、5090 服务器、5090 消费级桌面、8 GB 的 4060 笔记本，以及一台 96 GB RTX PRO 6000 工作站。三台租用服务器限制 CPU 线程并绑到 GPU 所在 NUMA 节点，用来模拟边缘主机的有效带宽；另两台消费者机器按原生配置运行。论文的 、 来自部署张量形状上的实测值，不是产品宣传峰值（§5.1、Table 1）。

平均 TTFT 不是 FreeToken 处处获胜：短的 W1 提示词更有利于 llama.cpp；Qwen3.6×W3 的平均 TTFT 有利于 KTransformers 的 GPU 预填路径。论文还检查最慢轮次：FreeToken 在各单元均低于 44 秒，而每个基线至少在一个设置中超过 150 秒。这里比较的是实验中的尾部观测，不是对所有未来请求的延迟上限（§5.2）。

Q：为什么作者特别强调最慢轮次？

A：代理客户端可能在长时间没有输出时超时。平均值接近的两个系统，仍可能因少数很慢的预填轮次带来不同的可用性；论文把这作为端到端交互证据，而非单独的缓存消融。

Figure 4：哪一部分设计得到了直接归因？

Figure 4(a) 对比相同 Qwen3.6、5090 条件下有无整层双缓冲，隔离了预填流水线。论文报告 8,192-token 分块约 1.19–1.22 秒完成，接近以 52.7 GB/s 读取 64.4 GB 专家池一次的时间；在 16k 输入上预填可达约 6.7k token/s。关闭第二缓冲后，4k、8k、16k 输入的吞吐分别下降 19%、25%、26%。这比端到端图更直接地支撑“重叠搬运与计算”这一设计（§5.3）。

Figure 4(b) 固定相同路由轨迹与缓存容量，对比专家放置策略的未命中率。在 RTX 5090 的服务容量下，Qwen 专家池有 37% 可缓存，DeepSeek 专家池只有 11% 可缓存；共享 LRU 的未命中率分别为 16%、39%，KTransformers 的放置策略为 41%、59%，llama.cpp 静态划分为 62%、89%。这验证短期路由局部性可利用；它单独不能证明带宽分工公式或 CPU 图内调度各贡献了多少 token/s（§5.3）。

Figure 5：换机器之后，结论还成立吗？

Figure 5 在五台消费者系统上重复 W2 编码代理负载。论文报告 FreeToken 相对最强可用基线在 3090、4090 上约为 1.3 倍，5090 服务器为 1.9 倍，5090 桌面为 2.1 倍，4060 笔记本为 1.8 倍。笔记本以 NVFP4 服务 Qwen3.6，达 39.3 token/s；由于权重精度不同，不能把它与 BF16 的台式机读数当作只改变硬件的一组严格对照（§5.3）。

两台 5090 使用相同 GPU 芯片、不同主机。论文报告从带宽更宽的服务器换到双通道内存桌面，FreeToken 的生成速度只下降 4%，而 llama.cpp 保留约 80% 的原速度。这与“减少对单一主机侧执行路径的依赖”的解释相符，但仍是具体主机组合的观测（§5.3）。

工作站实验又换了模型和任务：单张 RTX PRO 6000 运行 753B 参数的 GLM-5.2，FreeToken 为 14.9 token/s，llama.cpp 为 7.3 token/s；平均 TTFT 分别约 7.5 和 7.8 秒。KTransformers 在该工作站上没有可服务的配置，论文说明其专家内存需求或权重格式支持不满足条件。此例展示了可运行规模，不是普通 8 GB 笔记本也能运行 753B 的证据（§5.3）。

与已有方法相比，差别在哪里？

专家卸载并非新问题。论文 §6 把相关路线分成几类：有些系统靠预测或预取减少未命中；有些通过较低精度副本、替代或跳过专家减少搬运，但可能改变数值计算；还有系统把一部分专家交给 CPU，或在启动时把整层固定分到不同设备。FreeToken 保留原路由选中的专家计算，重点处理预测之后仍会发生的未命中，并让分配比例取决于部署机器的实测带宽。

因此，读这篇论文时应把“缓存带来更多命中”“未命中由两条路径并行服务”“代理状态在语义边界复用”看成互相补足的机制。若只说它使用了 LRU，就无法解释 Figure 3 的尾部首 token 时间；若只说它使用了 CPU，就无法解释 Figure 4 的缓存未命中差异。系统论文的因果链要把工作负载、内存层级、调度和实现开销连起来。

结论能推广到哪里？

最有依据的结论是：在论文测试的模型、精度和代理负载中，FreeToken 能把有限显存、PCIe 与主机带宽组合起来，提高可服务规模和交互生成速度。 Figure 4 提供了对预填双缓冲和缓存局部性的直接证据；Figure 3、5 则提供整体性能和跨机器证据。

部署前仍要核对完整专家池能否放进主机内存、权重格式与 CPU/GPU kernel 是否支持、是否能固定/注册 DMA 内存、能否腾出两层预填缓冲，以及目标负载是否有类似的长输入、历史编辑和专家局部性。论文还没有用 Figure 3–5 分离测出动态显存重建、FTW 启动布局和 策略各自的独立收益；不能把整体倍数分别归给它们。

评测范围也有边界。主要比较集中在两种 MoE 模型、四类负载和六台机器；三台服务器以线程约束模拟边缘主机，另两台消费者机器提供真实边缘验证。跨引擎代理轨迹可能分叉，所以论文没有比较总任务时长。能耗、持续高并发、多用户混部、长期显存抢占与其他模型家族的效果，还需要单独实验；这些是本文证据之外的待测问题，不等于系统已经在这些条件下失败（§5–7）。

Takeaway

  1. MoE 的“每 token 少算”没有消除完整专家池的存储成本；长输入与逐词生成需要不同的权重策略。
  2. FreeToken 的主线是预填阶段隐藏整层搬运、在代理语义边界复用状态，生成阶段先利用短期缓存局部性，再按实测带宽并行处理残余未命中。
  3. 判断证据时要分清：Figure 4 直接隔离了双缓冲和缓存放置；Figure 3、5 说明整体表现；后两者不能自动量化每个内部模块的单独收益。
  4. 使用者最终应查看目标机器的显存、主机内存与带宽，以及模型精度和代理负载。论文给出的是可适配资源的执行方法，不是跨机器固定的速度承诺。
