一张显卡跑大模型：FreeToken 如何让 CPU 与 GPU 合作

PAPER / 原文信息

论文信息

  • 题名： FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution
  • 作者： Shuo Yang、Xiaoze Fan、Melissa Pan 等
  • 版本： arXiv:2608.16157v1，2026-08-17

快速阅读

  • 问题： MoE 每次只用少数专家，整套专家权重却远超显存；长输入要搬运大量权重，逐词生成又会频繁遇到缓存未命中。
  • 做法： 输入阶段让搬运与计算重叠；生成阶段按机器实测带宽，把未命中的专家分给 GPU 缓存填充和 CPU 就地执行。
  • 证据： RTX 5090 上，两种模型的生成速度分别保持在 77–83 和 22–25 token/s；论文还报告了缓存未命中率的改善。
  • 边界： 这些数字来自论文指定的模型、硬件和负载；其他机器要重新测量带宽，不能直接套用速度结论。

为什么“只激活少数专家”还会卡顿？

混合专家模型（MoE）把计算分给许多子网络，论文把这些子网络称为“专家”。处理一个文本片段（token）时，路由器只挑少数专家参与。以论文中的 DeepSeek-V4-Flash 为例，模型总参数量为 284B，每个 token 只激活约 13B。计算量降下来了，全部专家的存放问题却没有消失（§1）。

显存放不下完整专家池时，权重必须留在主机内存，需要时再经连接主机与显卡的 PCIe 总线搬过去。一次长输入的各个 token 可能访问不同专家，合在一起几乎覆盖整层；进入逐词生成后，访问更稀疏，但所需专家不在显存缓存中时仍要等待。FreeToken 分别处理这两个阶段，而不是指望一套固定放置策略解决所有情况。

输入阶段：让搬运躲在计算后面

处理长输入时，FreeToken 在显存中留出两组整层缓冲。GPU 正在计算当前层时，另一组缓冲经 PCIe 接收下一层专家；下一层开始计算时，两组交换角色。搬运与计算在时间上重叠，减少逐层等待。这要求缓存能腾出两层空间；空间不足时，系统退回按需加载（§3.1）。

多轮工具调用还会改写早先的上下文。FreeToken 在思考段、工具调用等语义边界保存循环状态检查点；编辑后，从仍然有效的最深检查点继续计算。这里的收益取决于上层应用是否真的在这些边界编辑上下文，不能理解为任何修改都能免费复用。

生成阶段：一次未命中有两条路

逐词生成时，FreeToken 用一块共享显存缓存保留最近访问的专家；空间不足时优先淘汰最久未使用的项，这就是 LRU 策略。未命中的专家仍在主机内存中，有两种处理方式：搬到显卡执行并留在缓存，或者直接交给 CPU 执行。前者有后续复用价值，后者可利用 PCIe 搬运后剩下的主机带宽（§3.2）。

Q：CPU 参与执行，会不会改变模型输出？

A：两条路径分别计算各自专家的部分结果，再合并为同一 MoE 输出；论文描述的是执行位置的调整，并非减少参与计算的专家（§3.2）。

为了不让每个 token 都回到主机侧重新调度，FreeToken 把缓存候选选择、有效任务数和 CPU 分支提交纳入 CUDA Graph 的执行过程。这样，带宽分配才有机会转化为实际延迟收益（§4.1）。

实验结果能说明什么？

论文在 RTX 5090 上比较四类负载，包括单轮数学任务和多轮编码代理。Figure 3 的上半部分是逐词生成速度，下半部分是首 token 时间；两项指标回答的是不同问题。

在这台 5090 上，Qwen3.6-35B-A3B 的生成速度为 77–83 token/s，DeepSeek-V4-Flash 为 22–25 token/s。论文报告它们相对于各负载最强基线的优势分别为 1.8–2.3 倍和 1.5–1.9 倍。长时间多轮运行中，FreeToken 的生成速度相对于单轮结果保持在 12% 的变化范围内（§5.2）。这些是论文所测配置的结果，不是任意消费级显卡的保证值。

缓存是否真的帮上忙？Figure 4 的同路由轨迹对照显示，在论文所用 5090 容量下，共享 LRU 对两种模型的专家读取未命中率分别为 16% 和 39%；KTransformers 为 41% 和 59%，llama.cpp 为 62% 和 89%（§5.3）。这支持“近期路由具有可利用的局部性”，但不能单独证明带宽分配公式贡献了多少增益。

何时值得采用？

FreeToken 的优势来自显存有限、专家池较大、主机内存和 PCIe 都可参与工作这一组合。部署前需要在目标机器上测量 与 ；快速搬运路径还要求专家权重所在内存能够固定或注册，供设备直接访问（DMA，§4.2）。

论文的主要比较覆盖指定模型与六台机器，其中三台以限制 CPU 线程数的服务器模拟边缘主机。短输入、单轮任务的平均首 token 时间也并非处处领先。因而，最稳妥的结论是：它提供了一套可随机器带宽调整的分工方法，并在论文测试的长上下文与多轮负载中显示出优势；能耗、启动时间和大规模并发仍需另行验证。

Takeaway

  1. MoE 的稀疏激活降低计算量，但不会自动消除专家权重的存储和搬运成本。
  2. FreeToken 在长输入阶段重叠搬运与计算，在逐词生成阶段用缓存和两条并行执行路径处理未命中。
  3. 分工比例由目标机器实测带宽决定；看实验时要同时核对模型、硬件、负载与指标。
